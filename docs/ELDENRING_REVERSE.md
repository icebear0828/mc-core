# 艾尔登法环（eldenring.exe）逆向记录

对应 `docs/REVERSE_INTERFACES.md` 的每个接口，这里只记**证据**和**还没证实的部分**。写法规则同只狼：先只读，有证据才写；每条标明证据等级。

- 目标：`eldenring.exe` 版本 `2.7.1.0`，文件大小 `87,042,128` 字节。**所有 RVA 只对这一个版本有效**，上线前要换成签名或 RTTI 查找（只狼的教训：游戏更新就失效）。
- 运行环境：Steam 版，**离线、不经 EAC**。测试进程名是 `start_protected_game.exe`，据逆向方说明它是离线替换的 `eldenring.exe`（SHA256 一致，有 `steam_appid.txt`，未加载 EAC 驱动）。这是口头声明；**我们的装载器必须自检**（发现 EAC 相关模块或缺少 `steam_appid.txt` 就拒绝绑定并报错）。联网 + EAC 下做注入或内存读写有封号风险。
- 数据来源：全部来自逆向方的报告。他们的脚本在 `D:\code\Seep-Reverse-Lab`，**不在本仓库，原始时间序列（如 919 帧采样）也没有提供**，我们只拿到结论和快照 JSON。
- 代码：`adapters/eldenring/include/eldenring_live.hpp`（目前只有 `readVitals` / `readPlayerVitals`）。

证据等级：

| 等级 | 含义 |
|---|---|
| **A 实机** | 在运行中的游戏里读到、并和游戏内操作对照过 |
| **B 反汇编/部分实测** | 指令字节、跳转目标已逐条核对自洽；或只有一个静止样本；语义仍可能是推断 |
| **C 推断** | 没有直接证据，**不得写进代码** |

### 1.5 距离表（`WorldChrMan + 0x1F1C8`，**不要用**）

条目 `{ ChrIns* ; float distance ; u32 }`，16 字节，按存储值升序。近处实体满足经验公式 `Tab = |E − P| − 5.000`（7 个不同方位的敌人逐一核对，与相机位置无关，相机到玩家实测 2.2 m，已否定 "相机臂长" 假说）。远处/非活跃实体存储值陈旧（NPC 4500 实距 180.4 m 表值 27.5；NPC 2270 实距 109.2 m 表值 73.7），因此**顺序本身也不可信**。相对距离一律用 `PhysicsModule+0x70` 自己算。`< 5 m` 时表值是负数还是夹到 0 未测。

### 1.6 世界射线（`WorldRaycast`）

对象链（A）：

```
[Base + 0x3D7A0D0] → CSHavokManImp (vtable RVA 0x2B934E8)
   └ [+0x98] → CSPhysWorld (vtable 0x2B96978)
        └ [+0x08] → hknpWorld (vtable 0x2EF0DD8)
```

| 函数 | RVA | 说明 | 等级 |
|---|---|---|---|
| **包装函数（我们调用它）** | `0xC71D70`（`.pdata` 范围 `0xC71D70~0xC71DF1`） | 把 from/disp 拷成对齐副本，法线在帧内暂存后拷回调用方；引擎有 10 个业务调用点 | A（实调） |
| 底层函数 | `0xC71AA0` | 包装函数调用它；引擎另有 5 个直接调用点 | A（实调） |
| 旧函数 | `0xC71E00` | 带 `owner` 参数，只返回命中点；filter `0x02000058` | B（未实调） |

调用约定（x64，调用方视角）：

```cpp
bool cast_ray_wrapper(
    void*            physWorld,   // RCX = [CSHavokManImp + 0x98]
    uint32_t         filterMask,  // EDX
    const hkVector4* from,        // R8   必须 16 字节对齐（签名里是 movaps [r8]）
    const hkVector4* disp,        // R9   位移向量 = end - from，必须 16 字节对齐（movaps [r9]）
    hkVector4*       outHitPos,   // [RSP+0x20] movdqa 写回，必须对齐
    hkVector4*       outNormal,   // [RSP+0x28] movdqa 写回，必须对齐，可 NULL
    float*           outFraction  // [RSP+0x30] 可 NULL
);
```

- 7 个参数全部显式传，不要的传 NULL；"pos 可为 NULL" 对包装函数**没有证据**，一律传真实缓冲。
- 命中点 = `from + fraction × disp`。法线单位长度。
- 签名（逆向方扫描，**单一 exe 内唯一命中，跨补丁未验证**）：
  - 包装函数（36 字节）：`4C 8B DC 53 57 48 81 EC 88 00 00 00 41 0F 28 01 4D 8D 4B A8 41 0F 28 08 4D 8D 43 B8 48 8B 84 24 D0 00 00 00`
  - 底层（37 字节）：`48 8B C4 55 56 57 41 54 41 55 41 56 41 57 48 8D A8 38 FF FF FF 48 81 EC 90 01 00 00 48 C7 44 24 30 FE FF FF FF`
  - **我们的装载器必须自己扫描，恰好 1 处命中才绑定；0 处或多处则整个射线能力不可用（失败关闭）。**

filter 取值（实调，空旷地形）：

| filter | 引擎用途 | 实测 |
|---|---|---|
| `0x5D` | 通用，调用点里真的用法线 | 垂直下射命中 y=1.064，法线 (−0.049, 0.998, 0.045) |
| `0x5E` | 底层 fraction 查询 | 垂直命中 y=1.027（低 3.7 cm）；水平比 `0x5D` 深 0.24 m |
| `0xE0` | 4 点向下地面探测（调用点 2~5） | 与 `0x5D` 逐位相同 |
| `0x15` | 特殊交互 | 水平与 `0x5D` 逐位相同 |
| `0x02000058` | 旧函数（实体层） | 从玩家中心起射，0.21 m 处命中**玩家自己的胶囊体** |

- 我们用 `0x5D` 打地形。**实体层射线不做**：敌人命中用我们自己的包围盒（`Phys+0x70` + 尺寸）。
- 地面验证：玩家脚底 `Phys.y = 1.080`，命中 1.027~1.064；`from + fraction × disp` 残差 < 1e-5；法线模长 1.0000。
- 水平验证：打到某静态几何体，法线 (−0.718, 0.338, 0.609)，是斜面，**不是平整墙面**，还没有在平整墙上测过。
- 调用点 2~5（间距 `0x7D/0x79/0x77`）连发 4 条向下射线、只取位置，再 `subps/sqrtps` 求差向量，**推断**是 4 点着地姿态拟合（"载具/角色"没证据）。

没做的：从射线打敌人时 `0x5D` 的结果；调用线程（实调是从外部远程线程发起的，10 余次没崩，不能证明线程安全）；起点在几何体内部、超长位移、跨原点跳变的行为。

### 1.8 受击观测（只读）

用 50 Hz 轮询 `DataModule+0x138` 与玩家 `DamageModule+0x80`，捕获 5 次受击：伤害量与 HP 差精确一致（−82、−25、−25、−25、−9）。`+0x80` 的 `W=1.0`，是**位置点**（不是击退冲量）。后四次来自同一怪物多段连击，命中点完全相同。

- 能做到：重构受击时刻、伤害量、点位。
- 不能做到：看到攻击者、伤害类型，拦截或改写伤害。
- 该点位的坐标系（Havok 还是别的）和它是接触点还是攻击者位置，没有同一时刻的玩家坐标可对照，**语义仍是 C**。

### 1.11 阵营关系矩阵（敌我判定，B）

- `CheckTeamRelation`（`0x14051B5D0`）：`*(RelationObject**)(Base+0x3B283F0 + (teamA*79 + teamB)*8)`，再调该对象 `vfunc[0](this, {1,0,0})`。矩阵 79×79 共 6241 项（49,928 字节），`lea` 的 RIP 相对地址我方复算为 `0x143B283F0`。

## 4. 坐标系与原点

- Havok 空间有**浮动原点**：位置在原点附近几十米，原点按 8 m 的整数倍跳变。
- 玩家 `ChrIns+0x80` = 锚点 = `Havok − Block`（玩家样本：Havok `(−0.717,4.76,−1.39)`、块局部 `(−48.717,84.76,−65.39)`、锚点 `(48,−80,64)`，三者吻合）。敌人的锚点读自 `ChrIns+0xD0`；5 个敌人（含不同块）与玩家**同一个锚点** `(144,−64,112)`。

- 距离表见 §1.5（不用）。

实现约束：
1. 相对位置一律 `Phys(enemy).+0x70 − Phys(player).+0x70`，同一 tick 读。
2. 防撕裂：先读一次锚点，读所有位置，再读一次锚点；两次不同就丢弃这一 tick。
3. 速度用 `Phys+0x120`，不用位置差分；单帧位移 > `速度×dt + 5 m` 视为原点重定位，重置跟踪器。
4. 不写 `+0x120`；不做块原点换算。

未验证：远处（> 200 m）、不同区域/地牢的敌人是否同一锚点；`ChrIns+0x80/+0x90/+0xD0` 在玩家与敌人上含义不同的原因（"PlayerIns 继承特化" 与基类字段偏移不可变冲突，已否定）。

## 10. 逆向任务单：玩家受击状态移除 + 盾牌格挡（2026-10-09）

**目标（还原 MC）**：玩家被打时只掉血 + 变红 + 一点击退，**没有受击硬直动画、倒地、被打断**，且 MC 的受击间隔里有 0.5 秒无敌；右键举盾时，正面 180° 内的近战伤害被完全挡下（只有轻微后退），盾牌期间不能攻击。游戏原生的受击/格挡表现必须能**按需关掉**，不能影响敌人。

**已知（不用再查）**
- 敌我伤害都经 `ProcessDamageContext(0x140448910)(damageModule, attackerChr, hitContext*, u32, u8 isBlockedDeflect)`；`isBlockedDeflect != 0` 时跳过扣血（§3.2/§3.6）。最终伤害在 `0x140448627` 写入 `ctx+0x228`，本加载器已挂 `0x140448910` 入口、只对自己发起的敌人受击替换；对玩家受击尚未挂。

- `ApplySpEffect` = RVA `0x9F54A0`（rcx ChrIns, edx id；签名会匹配两次）。

**A. 受击状态移除（按价值排序）**
1. **玩家受击表现的总门**：从 `ProcessDamageContext` 对玩家受害者的路径出发，找出触发"受击反应动画/硬直/倒地"的那一处（函数 + 条件 + 读取的字段），回答能否在**不影响扣血**的前提下单点跳过。给 RVA、前后各 5 条反汇编、寄存器/栈位置；区分：轻受击 / 重受击 / 击飞倒地 / 处决类（grab）。

## 11. 射线 / 部件 / 碰撞 / 投掷物 / 受击拦截报告（逆向方 2026-10-09，我方审计）

## 12. 输入总闸门 / `+0x1A` / 手柄 / 相机函数引用（逆向方 2026-10-09 回复，我方审计）

**我方在 exe 里核对过（A）**
- `0x14067B020` = `48 8B 05 <rip> 0F B6 80 34 0C 00 00 C3`，读 `[[0x143D6D988]+0xC34]`；全局地址由 rip 相对算得 `0x143D6D988`，与报告一致。15 字节前缀在 exe 里唯一（可做签名：`48 8B 05 ?? ?? ?? ?? 0F B6 80 34 0C 00 00 C3`）。
- 报告列出的四个调用点字节全部对得上：`0x14065A3FF`（输入总调度，`cmovne ebx,edi`）、`0x140AFD927`（翻滚 `0x3E7`）、`0x140AFE7BC`（攻击）、`0x140AF8BAD`（移动速度）。置零函数 `0x14067A950`（`mov byte [rax+0xC34],0`）和 `0x140680AAA`（`mov byte [rdi+0xC20],1`）也对。
- XInput：导入表里有 `XINPUT1_4.dll` 和 `DINPUT8.dll`；`0x141F2AEB8` 处是 `mov ecx,ebx; call; test eax,eax; jne` 的 0..3 轮询循环。
- `0x140766C60`：对 exe 的**所有**代码节扫描，直接 call 引用只有 `0x140E2BF53`、`0x140E2BFF3`，8 字节指针引用 0 个（与报告一致）。**修正我之前的说法**：本 exe 有两个 `.text` 节（`0x1000` 与 `0x4C13000`，后者约 18 MB），我 §9 的扫描只覆盖了第一个；这次补扫后结论不变。

**报告的疏漏 / 需要保留的警惕**
1. `0x14067B020` 实际有 **6 个**调用者（两个 `.text` 都扫过）：`0x140257E12`、`0x14065A3FF`、`0x140AF8BAD`、`0x140AFD927`、`0x140AFE7BC`、`0x140AFED08`。报告只分析了 4 个，**`0x140257E12` 和 `0x140AFED08` 没有解释**。挂钩让它返回 1，影响面是全部 6 个。
2. **"打开菜单/地图会置位 `+0xC34`" 没有观测数据**。报告给的时间序列全是 CSMenuMan 的字段（`+0x1A/+0x1C/+0x1D/+0x1E/+0x90[..]`），没有 `+0xC34` 随菜单变化的记录。我们不依赖这一点（我们是主动强制它为 1），但"原生菜单如何触发"仍是推断。`0x14067B910` 实际是一个把 `+0xC00..+0xC20` 一整段（含 double、-1 哨兵）复位的函数，`+0xC20=0` 只是其中一条，说明该对象带计时/事件状态，不是单纯的布尔。
3. **门只覆盖移动 / 翻滚 / 攻击 / 总调度。相机不在其中**（相机由 `0x140766C60` 管）。要完全冻结玩家，两处都要挂。
4. 手柄走 XInput：因此 DirectInput 清键对手柄无效，**走输入总闸门是正确选择**（门在动作派发之后，键盘和手柄都管）。

**`+0x1A` 的结论（B+，日志本身我没看到）**：是 OS 光标捕获状态，不是菜单标志。地图打开时保持 1，读盘时变 0，ESC 菜单时"独立受鼠标焦点管辖"。与我们此前"+0x1A 不是菜单标志"一致。**加载器不读也不写它。**

**加载器计划（待你实测完再动手）**
1. 背包打开时：挂钩 `0x14067B020` 返回 1（输入总闸门）+ 挂钩 `0x140766C60` 返回 1（相机）。两个都用签名定位、唯一匹配才挂，失败则退回"清 DirectInput 鼠标按键 + 不冻结"。
2. 虚拟光标继续用 DirectInput 的 `lX/lY` 累计（相机冻结后鼠标增量仍会送到 DI）。
3. 关闭背包后钩子立即恢复原语义（只在我们的开关为真时返回 1）。
4. 实测验收：背包开着时 WASD / 翻滚 / 跳跃 / 攻击 / 手柄摇杆都无效，关掉后立即恢复，无粘键。

### 18.1 更正（2026-10-09，实测推翻了上面的推断）

§18 里"`0x140450120` 只会为玩家受击运行"是**我的错误推断**。实测（两次箭击，`HIT-IN` 有记录，`hit vfx: skipped` 无记录）说明钩子没拦下血液特效。重新读字节：

- `WorldChrMan` 全局 `0x143D69FF8`：`0x1404B875E`、`0x1404B8960` 的 `mov rax/rcx,[rip+..]` 解出即此值；之前的 `0x143D65F88` 是笔误，已被对方自己撤回。
- `WorldChrMan+0x1E538` = `CSBuddyMan`：`0x14050BFE5 mov [rsi+0x1E538],rax`；构造函数调用目标 `0x1404B6170` 吻合。`+0x1E508` 玩家实例读取吻合。
- `CSBuddyMan` 字段：`+0x20` 请求槽（构造/消费后写 -1，`0x1404B8952` `cmp [r15+0x20],0; jl` 跳过），`+0x24` 当前（`mov [r15+0x24],eax`），`+0x88` 忙计数（`cmp [r15+0x88],0; jg` 跳过生成），`+0x3C` 石碑 ID（`0x1404BBE29 mov edx,[rcx+0x3C]`）。
- 生成函数 `0x1404BBDD0(CSBuddyMan*)`：`rcx` 存入 r12，`+0x3C` 经 `0x140D28630` 查石碑行，行指针为 0 就走 `0x1404BC900` 中止——**只要求行存在，没有距离判断**。`+0x20` 在 `0x1404BBED9` 读取，BuddyParam 查表 `0x140D28010` 在 `0x1404BBF9E` 调用，NpcParam 查表 `0x140D27D60` 在 `0x1404BC060`。调度点 `0x1404B89C2` 吻合。
- 阵营偏移 `ChrIns+0x6C`：我们早已是 A 级（`kTeamTypeInChrIns`）。

**未证实（B/C）**
- “写 `+0x3C` 与 `+0x20` 下一帧就召唤”：控制流支持，但 `0x1404B89B0` 调用的 `0x1404BB9A0`（以玩家所在区域为参数，遍历并清理链表）可能改写 `+0x3C`，且 `0x1404B8959` 的前置条件（`[rdi+0x10]`）未解。必须先做只读监视（见任务单）。

- 销毁 `0x1404B82D0`：该地址字节是 `48 8B 51 78 4C ..`，**不是**回复里写的函数序言；ClearAll `0x1404B7100` 的调用目标吻合（B）。
- `ChrIns+0x1A0` 模型掩码、`+0x190→+0x28`：无字节。我们已有的隐藏办法（hide_mask）才是实测的。

**推翻**
- **`0x14044E090` 不是“落地复位”，不能调用。** 反汇编：先 `call 0x140438810`，查 SpEffect `0x8F`（`0x1404FA370`），**没有该特效**时执行 `mov dword [rax+0x34], 6`（该表 `+0x34` 的 6 在回复自己的表里是“强制摔死”），再 `call [vtbl+0x118]`、`0x1403EE730`、`0x140E40050`，最后 `[全局+0x10]+0x78=3` 并在条件满足时 `[全局2+0x9328]=1`。这是一条**重着陆/摔伤处理**，不是清零。`0x14045AF25` 的调用点是它的使用者。回复里“调用后恢复正常奔跑”没有字节依据。顺带：`+0x34` 写在 `[chr+0x190]+8` 那个模块，**不是** `FallModule(+0x70)`。

### 29.1 召唤实测（只读探针 `mc_er_buddylog.txt`，用户在 Limgrave 石碑处用骨灰，mc_er.log 2026-10-09）
- **A（实机读到）** 闲置：`+0x20=+0x24=-1`、`+0x3C=0`、`+0x88=-1`。
- **A** 用骨灰那一刻，同一次采样里 `+0x20=232000`、`+0x3C=+0x38=1042360100`（十位地图实体 ID，前四位 1042 是 Limgrave 瓦片 42_36）、`+0x44=1`；**16 ms 后**（下一帧）`+0x20` 清为 -1、`+0x24=232000`。即：道具使用代码**一次写入请求和石碑**，帧更新再消费。`+0x3C` 不是更新循环写的。
- **A** 石碑 ID 约 13 秒后回到 0，`+0x28` 变 1，`+0x24` 保持 232000，**离场/收回不会清 `+0x24`**。
- **A** `+0x80`：世界加载完成后变 1，退出世界变 0（和召唤无关，之前误以为是“已召唤”）。`+0x88` 一直 -1。
- **B（反汇编）** 请求值 = **骨灰 ID × 100 + 强化等级**：`0x1404BBEE2` 用 `0x51EB851F` 除以 100，商和余数分开用。232000 = 骨灰 2320、等级 0。**逆向方给的 21200000 / 21500000 / 23500000 对不上，别用。** `0x140D28010` 的 BuddyParam 查表参数来自 `0x1404B9C90` 返回的列表（`[rbx+0x10]`），不是请求值本身。
- **A** 虚表 RVA `+0x3B458B8`（逆向方说 `0x142A4F828`，错）。
- **未解**：生成位置是否取自石碑行（如果是，换地方写入也会出现在石碑处）；在石碑区外写入请求是否会被拒；`+0x38`、`+0x44` 是否也是必须的；骨灰 2320 是什么、`0x140D28630` 石碑行需要哪些实体 ID。
- **A（用户目测）** 召唤物出现在**玩家身前，随玩家朝向变化**（换方向召唤，出来的方向也变），不是固定在石碑位置。所以生成位置取自玩家，石碑 ID 只用来查石碑行（`0x140D28630`，行指针为空则中止）。
